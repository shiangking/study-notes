CS2030S Guide: Functions, Encapsulation, and OOP Basics

Primary source: Week 1 lecture notes, Units 3–4. This guide preserves the course ideas and code patterns, while adding connective explanations for exam revision.

1. In-depth summary & concept fundamentals

Functions act as abstraction mechanisms that separate what a computation does from how it is implemented. This creates a clear boundary—an abstraction barrier—between clients and implementers. In Java, this barrier is strongly enforced through return types and parameter types.

Encapsulation takes this a step further by bundling composite data types (fields/attributes) with the functions (methods) that operate on them into a Class. An instantiated class is an Object, which maintains the integrity and consistency of its own internal state.

Java distinguishes between primitive types (which directly store their literal values) and reference types (which store memory addresses pointing to objects in the heap). When two reference variables point to the same object, they create an alias. Mutating the object via one reference causes the change to be visible through all other references, which is a major source of bugs.

2. Core concepts & deep-dive breakdown

Defining composite data types and classes

When modeling real-world entities, we map nouns to classes, adjectives to fields, and verbs to methods:

class Circle {
  double x;
  double y;
  double r;

  double getArea() {
    return 3.14159265359 * r * r;
  }
}

Stack and heap memory aliasing

Reference variables store only the reference (pointer) to the object allocated in heap memory:

Circle c1 = new Circle();
Circle c2 = c1; // c1 and c2 reference the EXACT SAME object in heap memory

c1.r = 10.0;
System.out.println(c2.r); // Prints 10.0

Initialization rules: Local vs. Class fields

Variable Scope Default Value Uninitialized Access Result
Local Variable (inside method) None Compile-time error (variable might not have been initialized)
Class Primitive Field 0, 0.0, or false Accessible with default value
Class Reference Field null Compiles, but causes runtime NullPointerException if dereferenced

3. Exam traps & common pitfalls

# Exam Pitfall Root Cause Remedy
1 Aliasing Mutation Bugs Assuming c2 = c1 duplicates the object rather than copying the pointer address. Instantiate a distinct object instance with new when independent state is required.
2 Uninitialized Local References Forgetting that local variables in Java do not receive default values like fields do. Always assign local variables before accessing or reading them.
3 Dereferencing Null Fields Attempting to invoke methods on reference fields that were never initialized. Initialize internal reference fields inside constructors or upon declaration.

4. Active recall flashcards

Question Answer
What mechanism enforces the abstraction barrier of a Java function? Its parameter types and return type.
What is the default initial value of a class reference field? null
What occurs when two reference variables point to the same heap object? Aliasing (mutating the object via one reference affects both).
What happens if you read an uninitialized local variable in Java? It results in a Compile-Time Error.

5. Exercise 1 — Discrete Event Simulator I & OOP Fundamentals

Source: supplied Exercise 1 reference notes. This section connects the exercise implementation to the OOP principles introduced earlier on this page. Any additional clarification is explicitly labelled supplementary.

5.1 What is a discrete event simulator?

A discrete event simulator (DES) models a system whose state changes only at separate, instantaneous points in time called events. Between two consecutive events, nothing in the simulated system changes. The simulator can therefore jump directly from one event timestamp to the next instead of processing every possible clock tick.

Event at time 1.0  -- state changes
(no change between events)
Event at time 3.5  -- state changes
(no change between events)
Event at time 8.0  -- state changes

The simulator engine stores scheduled events in a priority queue. It repeatedly removes the next event, prints its representation through toString(), calls simulate(), and enqueues any new events returned by that method.

5.2 Three-layer architecture

LayerRoleKnows about
Simulator engine Manages the priority queue, advances simulated time, and invokes event behaviour. The general Event abstraction, including toString() and simulate().
Event hierarchy Represents state transitions such as arrival, service beginning, service ending, and departure. The domain entities required by each event.
Domain entities Store and control business state such as customer information and counter availability. Their own state and responsibilities, not the simulator's scheduling mechanism.

This separation keeps the simulator reusable. The engine does not need a large bank-specific conditional; it only asks each event object to simulate itself.

5.3 Entity modelling: encapsulation and Tell-Don't-Ask

Instead of passing unrelated primitive values such as a customer ID or counter ID everywhere, the program models meaningful concepts as classes. Each class owns the state and behaviour belonging to that concept.

ClassEncapsulated stateResponsibilitiesDesign reason
Customer int id, double arrivalTime, double serviceTime Provides its identity, arrival time, and required service duration. Represents an immutable request for service. It does not decide when service actually starts or ends.
Counter int id, boolean isAvailable Reports availability and performs state transitions through methods such as serve(Customer) and endService(). The counter, rather than an event, controls its own availability state. 
// Preferred: tell the counter what happened.
counter.serve(customer);

// Avoid exposing representation and mutating it externally.
// counter.available = false;

The first version follows Tell-Don't-Ask and information hiding. If the representation of counter state changes later, event classes need not change as long as the counter's public behaviour remains consistent.

5.4 Polymorphic event hierarchy

Each event type is a subclass of Event and overrides simulate(). This replaces a brittle event-type integer followed by a long if or switch statement.

Event subclassStored dependenciesState transition in simulate()New event(s)
Arrival Customer, Counter[] Scans counters from index 0. If one is available, the customer proceeds to service; otherwise the customer is rejected. ServiceBegin if a counter is free; otherwise Departure.
ServiceBegin Customer, Counter Calls counter.serve(customer) and computes the completion time from the actual service-start time. ServiceEnd at getTime() + customer.getServiceTime().
ServiceEnd Customer, Counter Calls counter.endService(), making the counter available immediately. Departure at the current event time.
Departure Customer Represents the terminal state of the customer's lifecycle. An empty array: new Event[] {}.

5.5 Customer lifecycle

  1. An Arrival event occurs at the customer's arrival time.
  2. The arrival searches for the first available counter.
  3. If a counter is available, a ServiceBegin event is produced.
  4. ServiceBegin marks the selected counter busy and schedules ServiceEnd.
  5. ServiceEnd frees the counter and schedules Departure at the same timestamp.
  6. Departure produces no more events.

If every counter is busy at arrival time, the customer skips the service events and proceeds directly to Departure.

5.6 Why completion time belongs in ServiceBegin

The service completion timestamp is:

completionTime = actualServiceStartTime + customerServiceTime

It is not generally:

arrivalTime + serviceTime

A customer might wait before service begins in later versions of the simulator. The customer knows the amount of service required, but cannot predict the scheduling delay. The ServiceBegin event knows the actual start timestamp through getTime(), so it is the correct place to calculate completion.

5.7 BankSimulation as the setup factory

BankSimulation extends Simulation. Its job is to parse the input, construct shared domain state, create the initial events, and return them to the generic simulator.

StepOperationKey implementation detail
1. Parse dimensions Read the number of customers n and counters k. int numOfCustomers = sc.nextInt();
int numOfCounters = sc.nextInt();
2. Allocate counter state Create and fill a Counter[]. Allocate new Counter[numOfCounters], then instantiate each counter from index 0 to k - 1.
3. Build initial events Create customers and their arrival events from the input pairs. Allocate new Event[numOfCustomers], then assign an Arrival object to every slot.
4. Provide events Override getInitialEvents(). Return the fully initialized Event[] to the simulator. 
Counter[] counters = new Counter[numOfCounters];
for (int i = 0; i < numOfCounters; i++) {
  counters[i] = new Counter(i);
}

Event[] initialEvents = new Event[numOfCustomers];
for (int i = 0; i < numOfCustomers; i++) {
  double arrivalTime = sc.nextDouble();
  double serviceTime = sc.nextDouble();
  Customer customer = new Customer(i, arrivalTime, serviceTime);
  initialEvents[i] = new Arrival(customer, counters);
}

5.8 Arrays store references, not automatically created objects

Event[] events = new Event[n];

This creates one array containing n reference slots. Every slot initially contains null; it does not create n event objects.

events[i] = new Arrival(customer, counters);

Each slot must be assigned an actual event before the simulator uses it. Calling a method through an uninitialized slot causes NullPointerException. If the array variable itself was never allocated, evaluating events[i] already dereferences null and also fails.

5.9 Why terminal events return an empty array

@Override
public Event[] simulate() {
  return new Event[] {};
}

The simulator expects to iterate through the returned array and enqueue its elements. An empty array means “this event produces zero successors” while preserving that contract. Returning null instead forces the engine to perform a special null check and risks NullPointerException.

Supplementary explanation: an empty collection or array is often preferable to null when “no results” is a normal, valid outcome. Both cases can represent zero elements, but only the empty array can be safely iterated without extra branching.

5.10 Exam traps and implementation pitfalls

TrapIncorrect approachCorrect patternWhy it matters
Constructor super() order Performing assignments before super(time). Place super(time) first in the constructor body. This is the constructor rule expected by the exercise environment and strict checkers.
Premature completion time Defining the end time as arrival time plus service time inside Customer. Calculate getTime() + customer.getServiceTime() in ServiceBegin. Arrival and actual service start may differ.
Null array slots Allocating new Event[n] and assuming it contains events. Assign an instantiated event to every slot. New reference arrays are filled with null.
Static counter IDs Using a static auto-incrementing nextId. Pass the loop index explicitly: new Counter(i). Static state persists across simulations in the same JVM and can make later tests start from the wrong ID.
Raw Javadoc tags Writing @param inside a Java parameter list. Put @param only inside a /** ... */ comment above the declaration. Javadoc tags are documentation syntax, not Java parameter syntax.
Monolithic event type Using one event class with an integer type and large conditional. Create one subclass for each event behaviour. Polymorphism localizes each transition and makes new event types easier to add.

5.11 Active recall

QuestionAnswer
Why use separate event subclasses instead of an event-type integer? Polymorphism lets each event own its simulate() behaviour, eliminating brittle conditionals and supporting extension without rewriting existing event logic.
Why call counter.serve(customer) instead of setting an availability field? The counter owns its state transition. This preserves information hiding and follows Tell-Don't-Ask.
Why does Departure.simulate() return an empty array instead of null? The simulator can iterate over an empty array safely; null violates the expected return contract and risks NullPointerException.
What does new Event[n] create? One array containing n reference slots initialized to null, not n event objects.
How does DES time advance? It jumps from the timestamp of one priority-queue event to the timestamp of the next event rather than ticking continuously.
Where should service completion time be calculated? In ServiceBegin, using the actual event time plus the customer's service duration.

5.12 What to remember for the exam

  • A DES changes state only at event timestamps and jumps directly between them.
  • The simulator engine handles scheduling; event subclasses handle transitions; domain entities own business state.
  • Polymorphism replaces event-type conditionals with overridden simulate() methods.
  • Use Tell-Don't-Ask: tell a counter to serve or finish rather than mutating its fields externally.
  • Compute completion from the actual service-start event time, not from arrival time.
  • Allocating a reference array does not instantiate the objects stored in its slots.
  • Return an empty event array for a terminal event rather than null.
  • Avoid static ID counters when multiple simulations may run in the same JVM.
  • BankSimulation constructs shared state and initial events; the generic engine executes them.
