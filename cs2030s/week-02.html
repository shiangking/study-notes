CS2030S Guide: Information Hiding, Objects, and Inheritance

Primary source: Week 2 lecture notes, Units 5–12. This guide preserves the course ideas and code patterns, while adding connective explanations for revision.

1. The central idea

Object-oriented programming is not merely putting data and methods in the same class. The aim is to give each abstraction control over its own representation and behaviour.

  • Information hiding protects implementation choices.
  • Tell, don’t ask keeps a task with the object that owns the relevant state.
  • Composition builds a complex object from simpler ones: HAS-A.
  • Inheritance models safe subtyping: IS-A.

The recurring question is: what is the client allowed to assume about this object?

2. Information hiding and constructors

Do not break the abstraction barrier

Suppose a client writes c.r = 10;. The client now assumes that a Circle stores its radius in a field named r. If the implementation changes to store diameter instead, client code breaks. The client has become a partial implementer.

private, public, and valid objects

class Circle {
  private double x;
  private double y;
  private double r;

  public Circle(double x, double y, double r) {
    this.x = x;
    this.y = y;
    this.r = r;
  }

  public double getArea() {
    return Math.PI * this.r * this.r;
  }
}

A private field or method is accessible only inside its class. A public member is part of the client-facing interface. The compiler enforces this protection at compile time.

A constructor initializes a new object. It has the same name as its class and no return type. It is invoked automatically by new Circle(...); it cannot be called like an ordinary method.

this refers to the current object. In this.x = x, the left side is the object field and the right side is the parameter. If a class declares no constructor, Java supplies a no-argument default constructor. If it declares any constructor, Java does not supply that default one.

3. Tell, don’t ask

Accessors and mutators are not a default design

Getters and setters are better than public fields because a setter can validate input. For example, a radius should not become non-positive. But providing a getter and setter for every field still leaks representation details and couples clients to the current structure.

public void setR(double r) {
  if (r > 0) {
    this.r = r;
  }
}

Instead of asking a circle for its centre and radius, then calculating containment in client code, tell the circle to perform the task:

if (circle.contains(p)) {
  // ...
}

Use this recognition rule: if client code calls two or more accessors on one object and combines the returned values to perform a meaningful computation, that computation probably belongs inside the object.

Heavy getter/setter use turns objects into passive data holders and pushes logic into clients, resembling procedural programming rather than object-oriented design.

4. Class fields and class methods

Instance members versus class members

MemberBelongs toExample
Instance fieldOne particular objectprivate double r;
Class fieldThe class; one shared copyprivate static int circleCount;
Instance methodOne particular objectc.getArea()
Class methodThe class itselfCircle.getCircleCount()
class Circle {
  private static int circleCount = 0;
  private double r;

  public Circle(double r) {
    this.r = r;
    circleCount++;
  }

  public static int getCircleCount() {
    return Circle.circleCount;
  }
}

A field declared static has one shared copy throughout program execution. Access it using the class name, such as Math.PI or Circle.circleCount; access through an instance is legal but misleading.

Use public static final for public constants such as Math.PI: static means class-level, final means it cannot be reassigned, and public makes it accessible to clients.

Why a static method cannot use this

A static method has no particular current object. Therefore it cannot use this or directly access instance fields. An instance method may access both its instance fields and class fields.

main is static because the JVM starts the program by invoking it before any instance needs to exist:

public static void main(String[] args) {
}

5. Composition and aliasing

Composition models HAS-A

class Circle {
  private Point c;   // a Circle HAS-A Point centre
  private double r;
}

Using a Point object instead of separate x and y fields avoids making Circle depend on how a point is represented. A Cylinder can similarly have a Circle base and a height.

Aliasing: shared references

Point p = new Point(0, 0);
Circle c1 = new Circle(p, 1);
Circle c2 = new Circle(p, 4);

c1 and c2 share the same Point object. If that point is mutated, both circles appear to move. This is called aliasing: two reference values refer to the same object.

Replacing c1's centre with a new point changes only c1's field:

c1.moveTo(new Point(1, 1));

However, shared mutable objects can still cause surprising effects elsewhere—for example, if two cylinders share one circle as their base. Avoid unnecessary sharing, or use immutable objects when appropriate.

6. Heap, stack, and parameter passing

What the model represents

RegionConceptual contents
StackMethod call frames, local variables, primitive values, and object references
HeapObjects dynamically allocated by new

Each method invocation creates a stack frame. It contains parameters, local variables, and this for an instance method. A static method has no this. Frames are removed when methods return, following last-in-first-out order.

Point p;
p = new Point(1, 2);

p is a stack variable holding a reference. new Point(1, 2) creates a Point object on the heap, runs its constructor, and assigns its reference to p.

Java is always pass-by-value

  • For a primitive argument, Java copies the primitive value. Changing a parameter does not change the caller's primitive variable.
  • For an object argument, Java copies the reference value. Both references can refer to the same object, so mutating that object is observable by the caller.

A method cannot reassign the caller's reference variable:

void reassign(Point p) {
  p = new Point(9, 9); // only changes this local parameter
}

This is the exam-safe statement: Java is not pass-by-reference; it is pass-by-value where the copied value may be an object reference.

7. Inheritance, subtyping, and casts

Inheritance models IS-A

class ColoredCircle extends Circle {
  private Color color;

  public ColoredCircle(Point centre, double radius, Color color) {
    super(centre, radius);
    this.color = color;
  }
}

ColoredCircle is a subclass of Circle; Circle is its superclass. super(...) calls the superclass constructor. A subclass can use inherited public methods but cannot directly access its superclass's private fields.

Use inheritance only when the subtype can safely stand in for the supertype. A coloured circle is a circle. A circle is not a point, and a cylinder is not a circle: those are HAS-A relationships, so composition is appropriate.

Compile-time and runtime type

Circle c = new ColoredCircle(p, 0, blue);

The compile-time type of c is Circle, because that is its declaration. The runtime type of its value is ColoredCircle, because that is the object created.

Upcasting is safe. A downcast requires an explicit assertion and is checked at runtime:

Circle c = new Circle(new Point(0, 0), 1);
ColoredCircle cc = (ColoredCircle) c; // compiles, then throws ClassCastException

8. Object, strings, and overriding

Every Java class ultimately inherits from Object. Useful inherited methods include equals(Object) and toString(). Java invokes toString() when an object is concatenated with a string.

@Override
public String toString() {
  return "{ center: " + this.c + ", radius: " + this.r + " }";
}

Without this override, printing a circle typically produces an unhelpful identity-like string such as Circle@.... This method makes the representation useful for debugging.

A method signature consists of its name and ordered parameter types. A method descriptor is the signature plus its return type. An instance method in a subclass overrides an inherited instance method when it has the same descriptor.

Always write @Override for an intended override. The compiler then reports a typo or mismatched signature instead of silently accepting a different method. Static methods with matching descriptors are hidden, not overridden.

10. Most important misconceptions to correct

  1. private is not merely style: it protects the abstraction barrier at compile time.
  2. Getters and setters are not automatically good OO design.
  3. static members do not belong to any individual object and cannot use this.
  4. Two reference variables can refer to the same mutable object.
  5. Java always uses pass-by-value, including for object references.
  6. Inheritance is for valid subtyping, not simply for convenient field or code reuse.
  7. A cast can compile and still fail at runtime with ClassCastException.
  8. Use @Override whenever you intend to override an inherited instance method.
