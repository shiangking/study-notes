CS2030S Guide: Polymorphism, Substitution, and Abstraction

Primary source: Week 3 lecture notes, Units 13–19. This guide preserves course concepts, terminology, and code patterns for exam revision.

1. In-depth summary & concept fundamentals

Polymorphism allows programs to be written in terms of high-level abstractions rather than concrete types, enabling extensibility without sacrificing static type checking.

Method Overloading allows multiple methods in the same class to share a name with differing parameter lists, resolved statically at compile time. In contrast, Method Overriding and Polymorphism allow an instantiated object to execute customized behavior based on its runtime type via dynamic dispatch.

The Liskov Substitution Principle (LSP) dictates that any subtype must safely substitute for its supertype without violating client assumptions. Abstract classes model shared state and incomplete hierarchies (IS-A), while Interfaces define shared capabilities (Can-Do) across unrelated class trees.

The golden rule of Java method invocation: Compile time chooses the method descriptor; Runtime chooses the implementation of that descriptor for instance methods.

2. Method overloading & constructor chaining

An overload occurs when methods share a name but differ in parameter count, type, or order (their method signature). Changing only the return type or parameter names does not create an overload.

public Circle() {
  this(new Point(0, 0), 1); // Invokes another constructor in the SAME class
}

this(...) delegates to another constructor in the same class to eliminate redundant code, whereas super(...) invokes the constructor of the immediate superclass.

3. Two-step method invocation & equals(Object)

Step When Determining Factor Outcome
Dynamic Binding Compile-Time Compile-time type of target and argument variables Selects the single most-specific method descriptor
Dynamic Method Lookup Runtime Actual runtime type of the target object Finds and executes the matching implementation

Properly Overriding equals(Object)

@Override
public boolean equals(Object obj) {
  if (obj instanceof Circle) {
    Circle circle = (Circle) obj;
    return circle.c.equals(this.c) && circle.r == this.r;
  }
  return false;
}

Defining equals(Circle c) is an overload, not an override. When passed to generic collections or methods typed as Object, Java selects equals(Object), which bypasses the overloaded method completely.

4. Liskov Substitution Principle & the final keyword

If $S <: T$, then any property provable for objects of type $T$ must hold for objects of subtype $S$. Compiling cleanly does not prove LSP compliance; semantic contracts and expected behaviors must be preserved.

Placement of final Enforced Constraint
final class Prevents class extension / inheritance entirely
final method Prevents subclasses from overriding the method
final field / variable Prevents variable reassignment after initialization

5. Abstract classes vs. interfaces

Feature Abstract Class Interface
Relationship IS-A relationship Can-Do (Capability)
State Can maintain instance fields and state Stateless (constants only)
Inheritance Single inheritance (extends) Multiple implementations (implements)

6. Exam traps & common pitfalls

# Exam Trap Root Cause Remedy
1 Accidental Overloading Writing equals(Circle) instead of equals(Object). Always annotate with @Override so compiler catches signature mismatches.
2 Static Method Invocation Expecting static methods to dispatch dynamically. Static methods resolve strictly by compile-time type; they are hidden, not overridden.
3 Interface Casting Bugs Assuming interface casts are verified fully at compile-time. Java allows interface casts if any subtype could implement it; verify runtime compatibility to avoid ClassCastException.

7. Active recall flashcards

Question Answer
Does changing only a method's return type create an overload? No. The return type is not part of the method signature and results in a compile error.
What is the difference between dynamic binding and dynamic method lookup? Dynamic binding occurs at compile time to pick the descriptor; dynamic method lookup occurs at runtime to pick the implementation.
Can an abstract class have zero abstract methods? Yes. An abstract class can have only concrete methods while still preventing direct instantiation.
What occurs if an object reference is null during an instanceof check? The expression safely evaluates to false without throwing an exception.
