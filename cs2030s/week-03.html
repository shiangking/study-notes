CS2030S Guide: Polymorphism, Substitution, and Abstraction

Primary source: Week 3 lecture notes, Units 13–19. This guide retains the lecture's terminology and examples, adding only connective explanations for revision.

1. The central idea

This week explains how Java supports flexible code without giving up static type checking.

  • Overloading lets one name support different parameter lists.
  • Overriding and polymorphism let an object choose customised instance behaviour according to its runtime type.
  • Liskov Substitution Principle (LSP) states the semantic responsibility required for safe inheritance.
  • Abstract classes and interfaces let us program against the behaviours a method needs, instead of unnecessary concrete details.

The key distinction throughout the week is: compile time chooses the method descriptor; runtime chooses the implementation of that descriptor for instance methods.

2. Unit 13 — Method and constructor overloading

What overloading means

Method overloading occurs when a class has two or more defined or inherited methods with the same name but different method signatures. A method signature consists of the method name plus the number, types, and order of parameter types.

public int add(int x, int y) {
  return x + y;
}

public int add(int x, int y, int z) {
  return x + y + z;
}

These are overloaded because their parameter counts differ.

public boolean contains(Point p) { ... }
public boolean contains(double x, double y) { ... }

These overloads let a client express a point either as a Point object or as Cartesian coordinates.

What does not create an overload

ChangeOverload?Why
Parameter names onlyNoNames are not part of a method signature.
Return type onlyNoReturn type is part of the descriptor, not the signature.
Parameter count, type, or orderYesThe signature changes.

Two methods may have different return types only if their parameter signatures also differ.

Constructor overloading and this(...)

Constructors can be overloaded too. A no-argument constructor can create a unit circle:

public Circle() {
  this(new Point(0, 0), 1);
}

this(...) invokes another constructor in the same class and avoids duplicate initialisation code. In contrast, super(...) invokes a superclass constructor. Static methods can also be overloaded.

3. Unit 14 — Polymorphism and semantic equality

Dynamic dispatch

void say(Object obj) {
  System.out.println("Hi, I am " + obj.toString());
}

The same expression, obj.toString(), may invoke Point::toString() for a point or Circle::toString() for a circle. The call is legal because the compile-time type is Object, which has toString(). The implementation selected depends on the target object's runtime type.

This runtime selection of an overridden instance method is dynamic dispatch (also described in the lecture as dynamic binding and dynamic method lookup).

Overriding equals(Object)

Object::equals(Object) tests whether two references refer to the same object. To define semantic equality for circles, override it:

@Override
public boolean equals(Object obj) {
  if (obj instanceof Circle) {
    Circle circle = (Circle) obj;
    return circle.c.equals(this.c) && circle.r == this.r;
  }
  return false;
}

instanceof checks whether the runtime object is a Circle (or subtype). The cast then gives Java a variable whose compile-time type is Circle, allowing access to the circle fields. Private fields are accessible here because the code is still inside class Circle, even though it accesses another Circle instance.

Why equals(Circle) is not enough

public boolean equals(Circle circle) { ... }

This is an overload, not an override, because its signature differs from Object::equals(Object). The annotation @Override correctly causes a compiler error.

In a generic method, the argument has compile-time type Object:

boolean contains(Object[] array, Object obj) {
  for (Object curr : array) {
    if (curr.equals(obj)) {
      return true;
    }
  }
  return false;
}

The compiler therefore commits to descriptor boolean equals(Object), not equals(Circle). At runtime, polymorphism can select Circle::equals(Object), Point::equals(Object), and so on. This keeps contains short, general, and ready for future classes without new instanceof branches.

4. Unit 15 — How Java invokes a method

For an instance method, Java resolves a call in two distinct steps.

StepWhenUsesDecides
Dynamic bindingCompile timeCompile-time target and argument typesWhich method descriptor / overload is called
Dynamic method lookupRuntimeRuntime type of the target objectWhich class supplies that descriptor's implementation

Step 1: choose one descriptor

For curr.equals(obj) in contains, both variables have compile-time type Object. The compiler selects boolean equals(Object). If several overloads can accept the arguments, Java chooses the most specific one: intuitively, the one whose parameter types are closest to the arguments' compile-time types.

If Java cannot determine a single most-specific overload, compilation fails. Once selected, the descriptor is stored in bytecode and does not change at runtime.

Step 2: find the implementation

If curr refers to a Circle at runtime, Java first searches Circle for an accessible method matching the chosen descriptor boolean equals(Object). If none exists, it searches the superclass, then its superclass, until Object. The first match is executed.

Class methods are different

Class methods (static methods) do not participate in dynamic dispatch. Java resolves them using the compile-time type of the target; the runtime type does not change the selected class method.

5. Unit 16 — Liskov Substitution Principle and final

The principle

If S <: T, an S object should be usable wherever a T object is expected, without breaking properties or expectations that client code relies on.

Lecture formulation: if f(x) is a property provable for objects x of type T, then f(y) should also hold for objects y of subtype S.

Course grading example

displayGrade(Course c, double marks) expects c.marksToGrade(marks) to return one of A, B, C, or F. A subtype that instead returns S or U breaks that expectation, even though it type-checks. This is an LSP violation.

An EasyCourse that returns only A, B, or C does not break this particular client: every output it can return is still handled by displayGrade.

Testing perspective

A subtype should pass the superclass's specification-based tests. A restaurant superclass promises that reservations can be made from 10:00 to 22:00. A LunchRestaurant that rejects 12:00–14:00 fails those tests and is not substitutable. A DigitalReadyRestaurant that also accepts outside those hours passes this particular test, provided the superclass specification does not require rejection outside operating hours.

The compiler cannot enforce LSP because it cannot determine semantic expectations such as allowed return values. Those expectations must be documented and tested.

Using final

Where final appearsEffect
Class declarationPrevents inheritance.
Method declarationPrevents overriding.
Field, local variable, or parameterPrevents reassignment.

Use final class Circle { } when the class should not be subclassed, or a final method when that behaviour must not be altered by subclasses.

6. Unit 17 — Abstract classes

An abstract class represents an incomplete abstraction: it is useful as a supertype, but creating an object of that general type does not make conceptual sense.

abstract class Shape {
  abstract public double getArea();
}

Shape is more specific than Object, because it guarantees getArea(), but more general than Circle. This allows a method to work with mixed shapes:

double findLargest(Shape[] array) {
  double maxArea = 0;
  for (Shape curr : array) {
    maxArea = Math.max(maxArea, curr.getArea());
  }
  return maxArea;
}

An abstract method has no body. An abstract class cannot be instantiated. A concrete subclass must implement every inherited abstract method or itself be declared abstract.

An abstract class may still have fields, constructors, concrete instance methods, and class methods:

abstract class Shape {
  private int numOfAxesOfSymmetry;

  public boolean isSymmetric() {
    return this.numOfAxesOfSymmetry > 0;
  }

  abstract public double getArea();
}

Giving Shape::getArea() a default value of 0 is unsafe: a subclass could forget to override it and silently produce an incorrect result. An abstract method shifts that error to compile time.

7. Unit 18 — Interfaces

Model a capability, not necessarily an IS-A relationship

An interface specifies what an entity can do. This lets unrelated class hierarchies share a capability without pretending that one is a kind of the other.

interface GetAreable {
  double getArea();
}

Interface methods are public and abstract by default, so public abstract may be omitted. Names often end in -able.

abstract class Shape implements GetAreable { ... }

class Flat extends RealEstate implements GetAreable {
  @Override
  public double getArea() {
    ...
  }
}

A concrete class implementing an interface must implement every abstract interface method. Now the method requires only the capability it actually uses:

double findLargest(GetAreable[] array) { ... }

Abstract class versus interface

Use an abstract class when…Use an interface when…
You need shared state or common base functionality within one class hierarchy.You need a capability shared across different class hierarchies.
The relationship is naturally IS-A.The relationship is “can do”.

A class can extend only one superclass but implement multiple interfaces. An interface can extend one or more other interfaces, but cannot extend a class. If class C implements interface I, then C <: I; a class can therefore have multiple supertypes.

Casting interfaces

Java permits some casts to an interface even where the current class does not implement it, because a future subclass might implement that interface. Such a cast can compile but still throw ClassCastException at runtime. An explicit cast tells the compiler to trust you; use it only when the runtime type truly supports the target interface.

Default methods and interface evolution

Adding a new abstract method to a published interface makes every existing implementation fail to compile until it implements the method. Java supports default methods, which provide an implementation in the interface, to help interfaces evolve without immediately breaking all existing implementations.

8. Unit 19 — Class diagrams

A class diagram is a compact design representation of classes, interfaces, and their relationships. It is part of UML, though the course uses a simplified form.

A class is drawn as a rectangle with three sections:

  1. Class name
  2. Fields
  3. Methods

Keep the field and method order consistent with the corresponding code. Use class diagrams to plan the abstractions and relationships before implementation, then translate the diagram into Java code.

10. Most important misconceptions to correct

  1. Changing only parameter names or only return type does not overload a method.
  2. equals(Circle) overloads; it does not override equals(Object).
  3. Overload choice uses compile-time types; overriding implementation choice uses runtime target type.
  4. Static methods are not dynamically dispatched.
  5. Passing the compiler does not prove LSP; LSP is about semantic expectations.
  6. An abstract class may contain concrete methods, and may even have no abstract methods.
  7. A concrete class cannot leave an inherited abstract method unimplemented.
  8. Interfaces model capabilities and can create multiple supertypes; they are not merely “abstract classes without fields.”
