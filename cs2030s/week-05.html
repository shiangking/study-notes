CS2030S Units 24–26: Generics, Type Erasure, and Unchecked Warnings

Source convention: The main definitions, examples, and rules below are based on the supplied lecture notes. Boxes labelled Supplementary clarification add background, edge cases, or corrections that make the Java behaviour more precise.

Topic overview

Java generics solve a tension created by polymorphism:

  • Using Object makes code reusable, but loses precise type information.
  • Writing one class for every combination of types preserves precision, but duplicates code.
  • Generics allow one reusable definition while letting the compiler track the actual types used at each location.
Object-based code: reusable, but imprecise
Generic code:      reusable and statically type-safe

Unit 24 studies how to write and use generic classes and methods. Unit 25 explains Java's implementation strategy—type erasure—and the resulting limitations involving runtime checks, static members, arrays, heap pollution, and overriding. Unit 26 explains what the compiler means by an unchecked warning, how to justify a necessary unchecked cast, and why raw types should be avoided.

Unit 24: Generics

1. Motivation: why Object is not enough

Suppose we want a class that stores two values. A specialised version for integers is straightforward:

class IntPair {
  private int first;
  private int second;

  public IntPair(int first, int second) {
    this.first = first;
    this.second = second;
  }

  int getFirst() {
    return this.first;
  }

  int getSecond() {
    return this.second;
  }
}

However, we may later need DoublePair, BooleanPair, or a pair containing two different types. Creating a class for every possible combination duplicates the same structure and behaviour.

The Object approach

Because every reference type is a subtype of Object, one general Pair class could store two Object references:

class Pair {
  private Object first;
  private Object second;

  public Pair(Object first, Object second) {
    this.first = first;
    this.second = second;
  }

  Object getFirst() {
    return this.first;
  }

  Object getSecond() {
    return this.second;
  }
}

This removes duplication, but discards the relationship between the stored values and the getter return types:

Pair foo() {
  return new Pair("hello", 4);
}

Pair p = foo();
Integer i = (Integer) p.getFirst(); // ClassCastException at runtime

The compiler only knows that getFirst() returns Object. The incorrect assumption that the first value is an Integer is therefore expressed as a narrowing cast, and the mistake is discovered only at runtime.

What we want the compiler to know

If the first component has type S and the second has type T, we want the compiler to enforce:

getFirst()  returns S
getSecond() returns T

Generics let the class definition state these relationships without fixing S and T to specific types.

2. Generic classes

class Pair<S, T> {
  private S first;
  private T second;

  public Pair(S first, T second) {
    this.first = first;
    this.second = second;
  }

  public S getFirst() {
    return this.first;
  }

  public T getSecond() {
    return this.second;
  }
}

S and T are declared between < and > after the class name. Inside the class definition they may be used as types for fields, parameters, local variables, and return values.

The constructor is still named Pair, not Pair<S, T>:

public Pair(S first, T second) { ... } // correct

Type variables must be declared before use:

class A {
  T x; // compile-time error: T has not been declared
}

3. Essential terminology

Term Meaning Example
Generic type A class or interface whose definition declares type parameters Pair<S, T>
Type parameter A type variable declared by a generic class, interface, constructor, or method S and T in class Pair<S, T>
Type argument An actual type supplied for a type parameter String and Integer in Pair<String, Integer>
Parameterized type The generic type used with specific type arguments Pair<String, Integer>
Type variable The parameter name used as a type within its scope S in private S first
Raw type A generic type used without type arguments Pair rather than Pair<String, Integer>

Parameter analogy

Method declaration:  void f(int x)       x is a value parameter
Method invocation:   f(10)               10 is a value argument

Generic declaration: class Box<T>        T is a type parameter
Generic use:         Box<String>          String is a type argument

Do not call String a type parameter in Pair<String, Integer>; it is a type argument. Do not call Pair<S, T> an instantiated object; it is a generic type declaration.

4. Using a parameterized type

Pair<String, Integer> foo() {
  return new Pair<String, Integer>("hello", 4);
}

Pair<String, Integer> p = foo();
String s = p.getFirst();
Integer i = p.getSecond();

For Pair<String, Integer>:

  • S is bound to String;
  • T is bound to Integer;
  • getFirst() has compile-time return type String; and
  • getSecond() has compile-time return type Integer.

Therefore, the compiler rejects the mistake before the program runs:

Integer i = (Integer) p.getFirst(); // compile-time error

The type system knows that p.getFirst() is a String, and the unrelated final class String cannot be cast to Integer.

Supplementary clarification — diamond syntax: Modern Java usually allows the constructor's type arguments to be inferred:

Pair<String, Integer> p = new Pair<>("hello", 4);

The <> is called the diamond operator. It does not remove generic checking; it asks the compiler to infer the arguments from the surrounding context.

Only reference types may be type arguments

This is illegal:

Pair<String, int> p; // compile-time error

Use the wrapper type instead:

Pair<String, Integer> p;

Autoboxing allows an int value such as 4 to be supplied where Integer is expected.

5. Passing a type parameter as another type's argument

A generic class may use its own type parameter as the type argument of another generic type:

class DictEntry<T> extends Pair<String, T> {
  // ...
}

Here:

  • DictEntry declares one type parameter, T;
  • String is the first type argument passed to Pair<S, T>; and
  • DictEntry's T becomes the second type argument passed to Pair.

For example, DictEntry<Integer> is a subtype of Pair<String, Integer>.

6. Generic methods

A method can declare its own type parameters even if its enclosing class is not generic:

class A {
  public static <T> boolean contains(T[] array, T obj) {
    for (T curr : array) {
      if (curr.equals(obj)) {
        return true;
      }
    }
    return false;
  }
}

Syntax rule

The type-parameter declaration appears before the return type:

modifiers <type-parameters> return-type method-name(parameters)

For example:

public static <T> boolean contains(T[] array, T obj)

The method's T is scoped to the entire method declaration and body. It expresses the intended relationship that the array elements and searched object have the same type.

Explicit type arguments

String[] words = { "hello", "world" };

A.<String>contains(words, "hello"); // valid
A.<String>contains(words, 123);     // compile-time error

A.<String>contains(...) explicitly binds method type parameter T to String.

Type inference

Usually Java infers a generic method's type argument:

A.contains(words, "hello"); // compiler infers T = String

Supplementary clarification — an important subtlety: The definition <T> contains(T[] array, T obj) does not absolutely guarantee that A.contains(words, 123) is rejected. Because Java arrays are covariant, the compiler may infer a broader common type such as Object, treating String[] as Object[]. The explicitly witnessed call A.<String>contains(words, 123) definitely fails. This is an interaction between method inference and array covariance, not a failure of generic classes in general.

7. Why an unbounded type variable has limited operations

Consider this attempted generic version of findLargest:

public static <T> T findLargest(T[] array) {
  double maxArea = 0;
  T maxObj = null;

  for (T curr : array) {
    double area = curr.getArea(); // compile-time error
    if (area > maxArea) {
      maxArea = area;
      maxObj = curr;
    }
  }
  return maxObj;
}

The compiler cannot assume that an arbitrary reference type T has a getArea() method. With no explicit bound, the only general guarantee is that values behave as Objects. This is why equals, toString, and other Object operations are available, but getArea() is not.

8. Bounded type parameters

We can restrict T to subtypes of GetAreable:

public static <T extends GetAreable> T findLargest(T[] array) {
  double maxArea = 0;
  T maxObj = null;

  for (T curr : array) {
    double area = curr.getArea();
    if (area > maxArea) {
      maxArea = area;
      maxObj = curr;
    }
  }
  return maxObj;
}

The bound gives the compiler two guarantees:

  1. Every T value supports getArea() because T <: GetAreable.
  2. The return type remains the precise array element type rather than being widened to GetAreable.

For a Circle[], the return type is Circle; for a Rectangle[], it is Rectangle. The caller no longer needs a narrowing cast.

Java uses extends for an upper bound even when the bound is an interface:

<T extends GetAreable>

Do not write <T implements GetAreable>.

Supplementary edge case: The lecture implementation returns null for an empty array and assumes valid areas can beat the initial value 0. In production code, define the empty-input contract explicitly and consider initializing from the first element after checking that the array is non-empty.

9. Self-referential bounds and Comparable

Java's Comparable<T> interface describes objects that can compare themselves with values of type T:

interface Comparable<T> {
  int compareTo(T other);
}

To order pairs by their first component, require the first component type to be comparable with itself:

class Pair<S extends Comparable<S>, T>
    implements Comparable<Pair<S, T>> {

  private S first;
  private T second;

  public Pair(S first, T second) {
    this.first = first;
    this.second = second;
  }

  public S getFirst() {
    return this.first;
  }

  public T getSecond() {
    return this.second;
  }

  @Override
  public int compareTo(Pair<S, T> other) {
    return this.first.compareTo(other.first);
  }

  @Override
  public String toString() {
    return this.first + " " + this.second;
  }
}

Read the declaration in two parts:

  • S extends Comparable<S>: S must support comparison with another S.
  • implements Comparable<Pair<S, T>>: this pair can compare itself with another pair having the same component types.

This is called a recursive or self-referential bound because the bound on S mentions S itself.

Pair<String, Integer>[] pairs = ...;
Arrays.sort(pairs); // uses Pair.compareTo

The pairs are ordered by their first String component because compareTo delegates to String.compareTo.

10. Generics versus the Object approach

Property Object-based Pair Generic Pair<S, T>
Reusable for many reference types Yes Yes
Getter return type Object Precise type variable
Caller casts required Usually No for correctly parameterized use
Wrong component assumption May fail at runtime Usually rejected at compile time
Relationship between inputs and outputs Lost Explicitly tracked
Raw-type compatibility Not applicable Possible, but unsafe and discouraged

Unit 25: Type Erasure

11. The key idea

Java generics perform their main safety work at compile time. After the compiler checks the program, it removes most generic type-argument information when producing bytecode. This implementation strategy is called type erasure.

Generic source code
      ↓ compile-time generic checking
Erasure of type parameters and arguments
      ↓ insertion of casts and bridge methods where required
Mostly non-generic bytecode executed by the JVM

The most important consequence is:

The compiler knows much more about generic type arguments than the JVM usually knows at runtime.

12. Code sharing versus code specialization

Different languages implement generic programming differently.

Strategy Main idea Examples from the lecture notes
Code specialization Generate code specialised for instantiated type arguments C++ and Rust at compile time; C# uses runtime support/specialisation
Code sharing through erasure Type-check generic source, then use one erased runtime representation Java

For Java, Pair<String, Integer> and Pair<Double, Boolean> do not become two separately defined runtime classes. Both are represented by the same raw runtime class, Pair.

Backward compatibility was an important motivation: generics were introduced in Java 5, and erased generic code could interoperate with older non-generic Java binaries and libraries.

13. The erasure transformation

Start with:

class Pair<S, T> {
  private S first;
  private T second;

  public Pair(S first, T second) {
    this.first = first;
    this.second = second;
  }

  public S getFirst() {
    return this.first;
  }

  public T getSecond() {
    return this.second;
  }
}

Conceptually, erasure produces something like:

class Pair {
  private Object first;
  private Object second;

  public Pair(Object first, Object second) {
    this.first = first;
    this.second = second;
  }

  public Object getFirst() {
    return this.first;
  }

  public Object getSecond() {
    return this.second;
  }
}

Erasure rule

  • An unbounded type parameter such as <T> erases to Object.
  • A bounded type parameter such as <T extends GetAreable> erases to its bound, GetAreable.
  • With multiple bounds, the erasure is the leftmost bound.

14. Compiler-inserted casts

Source code:

Integer i = new Pair<String, Integer>("hello", 4).getSecond();

Conceptual erased code:

Integer i = (Integer) new Pair("hello", 4).getSecond();

After erasure, getSecond() returns Object, so the compiler inserts a cast to restore the type promised by the checked source program.

This differs crucially from writing an unsafe cast manually:

  • For properly parameterized code, the compiler first proves that the generic relationships are consistent.
  • Only then does it generate the cast required by the erased representation.
  • If raw types or unchecked casts bypass the generic checks, that guarantee can be broken.

15. Compile time versus runtime knowledge

Consider:

Pair<String, Integer> p = new Pair<>("hello", 4);
Question Compiler JVM at runtime
May getFirst() be assigned to String? Yes; it knows S = String Executes erased method and cast generated by compiler
May getSecond() be assigned to String? No; it knows T = Integer Normally never sees this rejected program
Is the object a Pair? Yes Yes
Is the object specifically a Pair<String, Integer>? Statically tracked Usually unavailable because arguments were erased

This is why the following is illegal:

if (obj instanceof Pair<String, Integer>) { ... } // illegal

But checking the erased class is legal:

if (obj instanceof Pair) { ... }

16. Reifiable and non-reifiable types

A reifiable type is a type whose runtime representation retains enough information for the JVM to perform the relevant type check.

Typical reifiable types include:

  • primitive types;
  • ordinary non-generic classes such as String;
  • raw generic types such as Pair;
  • parameterized types with only unbounded wildcards, such as List<?>; and
  • arrays whose component type is reifiable, such as String[].

A concrete parameterized type such as Pair<String, Integer> is non-reifiable because the JVM normally sees only Pair after erasure.

Do not interpret “non-reifiable” as “not type-checked.” It is checked strongly at compile time; its full arguments are simply not generally available to runtime checks.

17. Why overloads cannot differ only by type arguments

This source code is illegal:

class A {
  void foo(Pair<String, String> p) { }

  void foo(Pair<Integer, Integer> p) { }
}

Both parameter types erase to Pair, producing the same effective signature:

void foo(Pair p)
void foo(Pair p)

Java therefore reports a name clash or duplicate method. Generic type arguments cannot be the sole basis of overloading because they do not produce distinct erased parameter types.

18. Class type parameters and static contexts

An instance belongs to a particular parameterized use:

B<Integer> bInteger = new B<>();
bInteger.setX(67);
Integer i = bInteger.getX();

The compiler can use the receiver's type B<Integer> to check instance-member calls.

A static member, however, belongs to the class itself and is shared by every parameterization. There is not one static field for C<String> and another for C<Integer>:

class C<T> {
  private static T x;       // illegal
  public static T getX() {  // illegal
    return x;
  }
}

Which T should the single shared x use? There is no instance receiver such as C<Integer> to provide an answer. Therefore, a static context cannot use the enclosing class's type parameter.

Static generic methods declare their own type parameters

class D<T> {
  public static <U> U identity(U x) {
    return x;
  }
}

U belongs to the static method invocation and is independent of the class's T. Using a different letter avoids falsely suggesting they are related.

19. Why arrays and generics do not mix cleanly

Arrays and generics make opposite runtime promises:

  • Arrays are reified: an array object knows its runtime component type and checks every store.
  • Parameterized generic types are erased: a Pair<String, Integer> object normally knows only that it is a Pair at runtime.

Imagine Java allowed:

Pair<String, Integer>[] pairArray =
    new Pair<String, Integer>[2]; // actually illegal Java

Object[] objArray = pairArray;
objArray[0] = new Pair<Double, Boolean>(3.14, true);

The runtime would see approximately:

Pair[] pairArray = new Pair[2];
Object[] objArray = pairArray;
objArray[0] = new Pair(3.14, true);

The array store check can confirm only that the inserted object is a Pair. It cannot distinguish Pair<Double, Boolean> from Pair<String, Integer>, so no ArrayStoreException could protect the generic promise.

Java prevents the direct creation:

new Pair<String, Integer>[2]; // illegal
new Pair<S, T>[2];           // illegal
new T[2];                    // illegal

However, declarations are allowed:

Pair<String, Integer>[] pairArray;
T[] array;

A declaration does not create an array and therefore does not yet require the JVM to represent a non-reifiable component type.

20. Heap pollution

Heap pollution occurs when a variable of a parameterized type refers to an object that is not compatible with that parameterized type's promise.

Conceptually, after the unsafe store above:

Static promise: pairArray[0] is Pair<String, Integer>
Actual object:  pairArray[0] is Pair<Double, Boolean>

The failure may appear later and far from the unsafe operation:

String str = pairArray[0].getFirst();

After erasure, the compiler-generated behaviour is conceptually:

String str = (String) pairArray[0].getFirst();

The actual first value is a Double, so the inserted cast throws ClassCastException.

Common sources of heap pollution include raw types, unchecked casts, and unsafe generic varargs or array workarounds. A compiler warning about an unchecked operation is therefore meaningful evidence that static guarantees are being bypassed.

21. Bridge methods

Type erasure can otherwise break overriding.

Source-level program

class Box<T> {
  void get(T value) {
    // ...
  }
}

class StringBox extends Box<String> {
  @Override
  void get(String value) {
    // programmer-defined implementation
  }
}

At source level, StringBox.get(String) overrides Box<T>.get(T) after T is bound to String.

The erasure problem

Conceptually, Box<T>.get(T) erases to:

void get(Object value)

But the subclass still has:

void get(String value)

These have different descriptors. Without help, a call compiled against the erased superclass descriptor get(Object) would not dynamically select get(String).

Compiler-generated bridge

The compiler adds a synthetic method to StringBox:

class StringBox extends Box {
  // Generated by the compiler
  void get(Object value) {
    this.get((String) value);
  }

  // Written by the programmer
  void get(String value) {
    // ...
  }
}

Now consider:

Box<String> box = new StringBox();
box.get("CS2030S");

The runtime sequence is:

  1. Compile-time method selection uses the generic superclass view.
  2. The stored runtime descriptor is the erased get(Object).
  3. Dynamic method lookup finds StringBox's bridge get(Object).
  4. The bridge casts the argument to String.
  5. The bridge delegates to the programmer-written get(String).

The bridge method preserves the overriding and polymorphic behaviour promised by the generic source code.

Supplementary correction: The bridge does not make the runtime directly dispatch an Object-descriptor call to get(String). Runtime dispatch first reaches the generated get(Object) bridge, which then calls get(String).

Unit 26: Unchecked Warnings

22. Why unchecked warnings exist

Java's compiler normally proves that operations involving generics are type-safe. Type erasure and non-reifiable types sometimes prevent it from proving a cast or call safe, even though the operation can be useful when implementing a generic data structure.

In such a situation, Java may issue an unchecked warning instead of rejecting the program:

An unchecked warning means that the compiler cannot fully verify the generic type-safety claim. It does not prove that the code is wrong, but responsibility for the missing proof has shifted to the programmer.

Compile with detailed generic warnings enabled:

javac -Xlint:unchecked Seq.java

This identifies the exact operation the compiler could not verify, the required type, the type it actually found, and the relevant type-variable declaration.

23. Prefer generic collections when an array is unnecessary

From the user's perspective, Java collections avoid many generic-array problems:

ArrayList<Pair<String, Integer>> pairList =
    new ArrayList<Pair<String, Integer>>();

pairList.add(0, new Pair<Double, Boolean>(3.14, true));
// compile-time error

The element type is checked at compile time. Furthermore, generic classes are invariant by default:

ArrayList<Pair<String, Integer>> pairList = new ArrayList<>();
ArrayList<Object> objList = pairList; // compile-time error

Even though Pair<String, Integer> <: Object, it does not follow that:

ArrayList<Pair<String, Integer>> <: ArrayList<Object>

Rejecting the alias prevents a caller from inserting an arbitrary Object into a list promised to contain only Pair<String, Integer> values.

ArrayList still uses an array internally. The library implementation has to manage the same low-level representation problem, which is why understanding the unchecked cast remains important when implementing generic data structures.

24. Implementing Seq<T> with an array

We may want a fixed-size generic sequence:

class Seq<T> {
  private T[] array;

  public Seq(int size) {
    this.array = (T[]) new Object[size];
  }

  public void set(int index, T item) {
    this.array[index] = item;
  }

  public T get(int index) {
    return this.array[index];
  }
}

Java forbids new T[size] because T is non-reifiable: the JVM does not know the actual component type needed to create and protect that array. The implementation therefore creates an Object[] and casts the reference to T[].

The compiler reports:

warning: [unchecked] unchecked cast
  required: T[]
  found:    Object[]

After erasure, the JVM can confirm only that the object is an Object[]. It cannot verify the stronger source-level claim that the array should behave as an array of the unknown T.

25. How the unchecked cast can become unsafe

Suppose Seq exposes its internal array:

public T[] getArray() {
  return this.array;
}

Client code can now create an alias with the actual backing Object[]:

Seq<String> seq = new Seq<String>(4);
Object[] objArray = seq.getArray();
objArray[0] = 4;

String value = seq.get(0); // ClassCastException

The static promise says that seq.get(0) returns String. Due to erasure, the generated code conceptually contains:

String value = (String) seq.get(0);

The internal array actually contains an Integer, so the compiler-inserted cast fails.

Supplementary precision: Merely writing seq.get(0); and discarding the result may not require a runtime cast. Assigning it to String, returning it from a String method, or otherwise using it in a context that requires String exposes the ClassCastException.

This example demonstrates heap pollution: a location treated as holding values of type T contains a value that violates that promise.

26. Informal type-safety proof for the restricted Seq<T>

Remove getArray() so clients cannot obtain or mutate the backing array directly:

class Seq<T> {
  private T[] array;

  public Seq(int size) {
    this.array = (T[]) new Object[size];
  }

  public void set(int index, T item) {
    this.array[index] = item;
  }

  public T get(int index) {
    return this.array[index];
  }
}

The human justification is an invariant argument:

  1. array is private, so ordinary clients cannot directly access it.
  2. The constructor initially fills the backing array only with null, which is valid for every reference type T.
  3. The only ordinary write operation is set(int, T).
  4. The compiler ensures that correctly parameterized callers pass only values compatible with that instance's T.
  5. Therefore, every non-null value retrieved from the backing array was previously accepted as a T.
  6. Consequently, the cast inserted when get is used as a T will succeed, provided no raw type, unchecked operation, reflection, or other unsafe back door breaks the invariant.

This is an informal proof of representation safety. The cast itself is not magically safe; encapsulation and the controlled write path make it safe under the stated assumptions.

Proof obligations to check

Before suppressing the warning, verify all of the following:

  • The unsafe representation is private and does not escape.
  • Every write is checked through the generic API.
  • No method returns the backing array directly.
  • No raw-type or unchecked client can inject incompatible values within the assumed scope.
  • The cast is used only to implement the representation, not to claim that an arbitrary object has type T.
  • Future maintainers can understand and preserve the invariant.

If any condition fails, the warning may represent a real route to heap pollution.

27. Suppressing a justified warning

Once the cast has been justified, suppress only that exact warning:

class Seq<T> {
  private T[] array;

  public Seq(int size) {
    // The backing array is private and never exposed. All writes occur
    // through set(int, T), so every stored value is compatible with T.
    @SuppressWarnings("unchecked")
    T[] a = (T[]) new Object[size];
    this.array = a;
  }

  public void set(int index, T item) {
    this.array[index] = item;
  }

  public T get(int index) {
    return this.array[index];
  }
}

The correct spelling is:

@SuppressWarnings("unchecked")

It contains two p characters in Suppress.

The annotation hides the warning; it does not change the program, insert a safety check, or fix unsafe code.

Minimal and ethical suppression

The annotation can target several declaration scopes, but use the narrowest permitted scope. In CS2030S, apply it only to the local variable declaration containing the justified cast.

Do not annotate the whole class or method merely for convenience. A broad annotation may hide unrelated warnings introduced later.

Every suppression should include a comment explaining:

  1. what operation is unchecked;
  2. why the compiler cannot prove it;
  3. the invariant that makes it safe; and
  4. how the code prevents the unsafe representation from escaping.

Treat the warning as a proof obligation, not as cosmetic output to remove.

28. Why a temporary local variable is used

@SuppressWarnings applies to declarations, not to an assignment expression by itself. Therefore, this is the precise pattern used in the constructor:

@SuppressWarnings("unchecked")
T[] a = (T[]) new Object[size];
this.array = a;

The warning is attached only to a's declaration. Annotating a broader scope would suppress more warnings than necessary.

29. Raw types

A raw type is a generic class or interface used without type arguments:

Seq s = new Seq(4); // raw Seq

Raw types exist primarily for backward compatibility with Java code written before generics were introduced in Java 5. They approximate the erased view of generic code and disable important generic checks.

Compare:

Seq<String> strings = new Seq<>(4);
strings.set(0, 1234); // compile-time error

with:

Seq raw = strings;
raw.set(0, 1234); // unchecked warning, but compiles

String value = strings.get(0); // ClassCastException

The raw reference bypasses the generic promise and pollutes the same object later viewed as Seq<String>.

Raw and parameterized assignments

Java permits raw and parameterized code to interoperate for migration compatibility:

  • Assigning a parameterized value to a raw variable loses type information.
  • Assigning a raw value to a parameterized variable generally produces an unchecked warning.

Supplementary precision: Do not interpret this as an ordinary, fully safe subtype relationship in both directions. One direction discards generic information; the other relies on an unchecked conversion that the compiler cannot verify.

30. Detecting raw types

Ask the compiler to report accidental raw-type usage:

javac -Xlint:unchecked -Xlint:rawtypes Seq.java

The two categories answer different questions:

Warning Meaning
[rawtypes] A generic type was used without its required type arguments.
[unchecked] A generic cast, conversion, or method call could not be fully verified.

A raw call such as raw.set(0, 1234) may generate both kinds of warning: the declaration uses a raw type, and the call cannot enforce T.

31. Raw types and instanceof

Because concrete type arguments are erased, this is illegal:

obj instanceof Seq<String> // illegal: Seq<String> is non-reifiable

At this point in the course, the permitted runtime check is:

obj instanceof Seq

This checks only the erased runtime class and says nothing about its original type argument.

Supplementary preview: After wildcards are introduced, obj instanceof Seq<?> expresses the same available runtime check without using a raw type. Until then, the raw operand is the lecture's temporary exception to the rule against raw types.

32. How to respond to an unchecked warning

Use this decision procedure:

  1. Compile with -Xlint:unchecked and locate the exact unchecked operation.
  2. Try to redesign the code so the operation is statically checkable—prefer a generic collection when appropriate.
  3. Identify the runtime representation after erasure.
  4. State the invariant needed for the cast or call to remain safe.
  5. Check every way that invariant might be broken, especially aliases, exposed arrays, raw types, and unchecked casts.
  6. If safety cannot be justified, fix the design; do not suppress the warning.
  7. If safety can be justified, document the proof and suppress only the smallest local declaration allowed.
  8. Recompile with both -Xlint:unchecked and -Xlint:rawtypes to ensure no unrelated warnings were hidden.

Problem-solving procedures

33. How to analyse generic code

  1. Locate every type-parameter declaration: class-level <T> or method-level <T>.
  2. Determine the scope of each type variable.
  3. Substitute the supplied or inferred type arguments into fields, parameters, and return types.
  4. Check each bound and list the operations that the bound guarantees.
  5. Identify raw types or unchecked casts that may bypass safety.
  6. Only after source-level checking, imagine erasure if the question concerns runtime behaviour.

34. How to compute erasure

  1. Replace each unbounded type variable with Object.
  2. Replace each bounded type variable with the erasure of its leftmost bound.
  3. Remove type arguments from parameterized types.
  4. Insert casts where client code needs to recover the statically promised type.
  5. Check whether erased methods create a signature clash.
  6. Check whether inheritance requires a bridge method to preserve overriding.

35. How to analyse generic arrays and heap pollution

  1. Ask whether the proposed array component type is reifiable.
  2. If code directly creates an array of a concrete parameterized type or T, predict a compile-time error.
  3. If an unchecked cast or raw array is involved, record the array's real runtime component type.
  4. Check what the runtime store test can actually see after erasure.
  5. Compare the variable's static generic promise with the actual stored object.
  6. Locate the later compiler-inserted cast where heap pollution may become ClassCastException.

Common mistakes and exam traps

  1. Confusing a type parameter (T) with a type argument (String).
  2. Calling Pair<String, Integer> a generic declaration instead of a parameterized type.
  3. Using primitive int as a type argument instead of Integer.
  4. Forgetting that a constructor is declared as Pair(...), not Pair<S, T>(...).
  5. Using a type variable without declaring it.
  6. Placing a generic method's <T> after the return type.
  7. Assuming an unbounded T has domain-specific methods.
  8. Writing implements inside a bound; Java uses extends for both class and interface upper bounds.
  9. Assuming generic type arguments remain fully available at runtime.
  10. Believing erasure removes compile-time safety; checking happens before erasure.
  11. Overloading methods whose parameter types differ only by generic arguments.
  12. Using the enclosing class's type parameter in a static context.
  13. Assuming each parameterized type has separate static fields.
  14. Creating new T[] or new Pair<String, Integer>[].
  15. Ignoring unchecked warnings that may indicate heap pollution.
  16. Predicting ArrayStoreException when the runtime can see only the raw component type Pair; the delayed failure is typically ClassCastException.
  17. Thinking a bridge method is programmer-written or source-visible; it is generated by the compiler.
  18. Thinking a bridge is an ordinary overload with independent behaviour; its purpose is to preserve source-level overriding after erasure.
  19. Treating every unchecked warning as proof of an error; it means the compiler cannot prove safety.
  20. Treating a warning as harmless without supplying the missing human proof.
  21. Suppressing "unchecked" over an entire method or class instead of the smallest declaration.
  22. Forgetting that suppression hides diagnostics but does not change runtime behaviour.
  23. Exposing a backing array whose safety depends on controlled access.
  24. Using a raw type such as Seq rather than Seq<T> or a concrete parameterized type.
  25. Suppressing warnings caused by raw-type pollution rather than removing the raw type.
  26. Misspelling @SuppressWarnings as @SupressWarnings.
  27. Assuming raw-to-parameterized conversion is fully safe because Java permits it for compatibility.

What to remember for the exam

  • Generics provide reusable code while preserving relationships between types at compile time.
  • A type parameter is declared; a type argument is supplied; their combination forms a parameterized type.
  • Only reference types can be type arguments, so primitives require wrappers.
  • A generic method declares <T> before its return type.
  • An upper bound such as <T extends GetAreable> both restricts permitted types and makes the bound's methods available.
  • Java type-checks generics first and erases most type arguments afterward.
  • Unbounded parameters erase to Object; bounded parameters erase to their bound.
  • The compiler inserts casts at use sites to recover types promised by the generic source program.
  • Concrete parameterized types are generally non-reifiable, so their full arguments cannot usually be checked at runtime.
  • Methods cannot be overloaded solely by different type arguments because the erased signatures clash.
  • A class's type parameter cannot be used by static members; a static generic method declares its own independent parameter.
  • Generic array declarations are allowed, but direct instantiation of arrays with non-reifiable component types is forbidden.
  • Heap pollution breaks a parameterized variable's static promise and can cause a delayed ClassCastException.
  • Bridge methods are compiler-generated erased-signature methods that delegate to the programmer's specialised override, preserving polymorphism.
  • An unchecked warning means the compiler cannot prove generic type safety; it is not automatically proof that the code is unsafe.
  • A necessary unchecked cast creates a human proof obligation based on a clearly stated representation invariant.
  • A private Object[] backing array can safely implement a restricted Seq<T> only when all writes accept T and the array never escapes.
  • @SuppressWarnings("unchecked") should be applied minimally and accompanied by a justification; it hides a warning but fixes nothing.
  • Generic collections are invariant by default, preventing the unsafe aliases permitted by covariant arrays.
  • A raw type omits type arguments, disables generic checks, and exists mainly for pre-Java-5 compatibility.
  • Use -Xlint:unchecked -Xlint:rawtypes to expose unchecked operations and raw-type usage.
