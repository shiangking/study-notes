CS2030S Guide: Wrapper Classes, Runtime Class Mismatch, and Variance

Primary source: supplied lecture notes for Units 20–22. Obvious transcription errors in the source code have been corrected; supplementary edge cases are marked as such.

1. The big picture

These three units expose places where Java's convenient abstractions move some safety or cost away from the line of code where it originates:

  • Wrapper classes let primitive values participate in object-based APIs, but may hide conversions, allocations, and null-related failures.
  • Narrowing casts let a program recover a concrete subtype after treating an object abstractly, but the claim may fail at runtime.
  • Array covariance lets an array of a subtype be used as an array of a supertype, but an apparently valid write can fail at runtime.

The shared exam strategy is to track both the compile-time type of each expression and the runtime class of the object to which it refers.

2. Unit 20 — Wrapper classes

Why wrappers exist

Java's primitive types are not classes, do not participate in inheritance, and are not subtypes of Object. A wrapper class encapsulates one primitive value in an object so that it can be used by polymorphic code or APIs requiring a reference type.

PrimitiveWrapperPrimitiveWrapper
byteBytefloatFloat
shortShortdoubleDouble
intIntegercharCharacter
longLongbooleanBoolean
 
Integer boxed = Integer.valueOf(4); // int -> Integer
int unboxed = boxed.intValue();     // Integer -> int

Autoboxing and auto-unboxing

Boxing converts a primitive to its wrapper type. Unboxing extracts a primitive from a wrapper. Java inserts these conversions automatically when required:

Integer x = 4; // autoboxing: Integer.valueOf(4)
int y = x;     // auto-unboxing: x.intValue()

int z = x + 2; // x is unboxed before arithmetic
x++;           // unbox, increment, then box the result

A wrapper object is immutable. Thus x++ does not mutate an Integer object; it produces a primitive result and assigns a wrapper for that result back to x.

Performance cost

Double sum = 0.0;
for (Integer i = 0; i < Integer.MAX_VALUE; i++) {
  sum += i;
}

This version repeatedly unboxes values for arithmetic and boxes results back into immutable wrapper objects. The concise syntax hides that work. A primitive double accumulator and int counter avoid most of the overhead and are preferable for performance-sensitive numerical code.

Equality

For primitives, == compares values. For wrapper references, == compares object identity. Use equals to compare wrapped values:

Integer a = Integer.valueOf(1000);
Integer b = Integer.valueOf(1000);

System.out.println(a == b);      // unreliable as a value comparison
System.out.println(a.equals(b)); // true

Supplementary warning: Java may cache and reuse some wrapper instances, so == may appear to work for certain values. This is exactly why it is unsafe as a general value comparison.

Null unboxing edge case

Integer n = null;
int value = n; // NullPointerException at runtime

The assignment compiles, but there is no primitive value to extract from null. This is a NullPointerException, not a ClassCastException.

3. Unit 21 — Runtime class mismatch

Abstraction forgets concrete information

GetAreable findLargest(GetAreable[] array) {
  double maxArea = 0;
  GetAreable maxObj = null;

  for (GetAreable curr : array) {
    double area = curr.getArea();
    if (area > maxArea) {
      maxArea = area;
      maxObj = curr;
    }
  }
  return maxObj;
}

The method is reusable because it works over the GetAreable interface. Its return type promises only a GetAreable, even if the returned object happens to be a Circle at runtime.

Compile-time type versus runtime class

ConceptDetermined byWhat it controls
Compile-time typeThe declaration and static type rulesWhich operations the compiler permits
Runtime classThe object actually createdDynamic method lookup and whether a narrowing cast succeeds

Widening and narrowing

Assume Circle <: GetAreable.

Circle c = new Circle(...);
GetAreable ga = c; // widening: implicit and safe

Widening from a subtype to a supertype is safe because every Circle satisfies the GetAreable contract.

GetAreable ga = findLargest(array);
Circle c = (Circle) ga; // narrowing: explicit cast required

Narrowing from a supertype to a subtype requires an explicit cast because not every GetAreable is a Circle.

What a cast means

A cast changes how the compiler is allowed to view a reference expression. It does not modify the object or convert it into an instance of another class.

GetAreable ga = new Rectangle(...);
Circle c = (Circle) ga; // compiles, then throws ClassCastException

The compiler accepts that the cast is structurally possible. At runtime, Java checks the actual object. A Rectangle is not a Circle, so the runtime check fails.

StageQuestion askedPossible outcome
Compile timeCould these reference types legally be related?Compile-time error or successful compilation
RuntimeIs this actual object compatible with the target type?Successful cast or ClassCastException

Checking before casting

if (ga instanceof Circle) {
  Circle c = (Circle) ga;
  // use c safely here
}

instanceof protects a genuinely necessary cast. However, frequent checks may signal that the abstraction does not expose the behaviour the client actually needs. Prefer using the object through its interface when possible.

Supplementary edge case: casting null to a reference type succeeds and produces null; dereferencing it later may cause NullPointerException.

4. Unit 22 — Variance

Definition

Variance describes how a subtype relationship between component types affects the relationship between complex types constructed from them. Let C(S) be a complex type formed from component type S, and suppose S <: T.

RelationshipDefinitionDirection
CovariantC(S) <: C(T)Preserves the subtype direction
ContravariantC(T) <: C(S)Reverses the subtype direction
InvariantNeither relationship follows in generalAllows neither direction by default

Java reference arrays are covariant

For Java reference arrays, if S <: T, then S[] <: T[]. Since Integer <: Object, Java therefore permits:

Integer[] intArray = {
  Integer.valueOf(10),
  Integer.valueOf(20)
};

Object[] objArray = intArray;

This is convenient for read-oriented code: anything read from an Integer[] is certainly an Object.

Why writable covariant arrays are unsafe

Integer[] intArray = { 10, 20 };
Object[] objArray = intArray;
objArray[0] = "Hello!"; // compiles, then throws ArrayStoreException

At compile time, objArray has type Object[], and a String is an Object, so the write is allowed. At runtime, the actual array object is still an Integer[]. Java checks the array's runtime component type and rejects the String with ArrayStoreException.

Operation through Object[]Compile-time resultRuntime result for actual Integer[]
Read an element as ObjectAllowedSafe: an Integer is an Object
Store an IntegerAllowedSucceeds
Store a StringAllowedArrayStoreException

Arrays versus generic collections

Arrays preserve their component type at runtime, enabling the runtime store check. Java generic classes such as List<T> are invariant by default:

List<Integer> ints = ...;
// List<Object> objs = ints; // compile-time error

The invariant rule rejects the dangerous alias at compile time. Later generic wildcard syntax provides controlled forms of covariance and contravariance.

6. Step-by-step exam procedure

  1. Write down the compile-time type of every relevant variable and expression.
  2. Write down the runtime class of every created object or array.
  3. Mark every implicit boxing or unboxing conversion.
  4. For a cast, check whether the actual object is an instance of the target type.
  5. For an array write, check the array object's actual runtime component type.
  6. Name the exact failure: NullPointerException, ClassCastException, or ArrayStoreException.

7. Common mistakes and exam traps

  1. Writing Int instead of Java's primitive type int.
  2. Assuming a primitive is a subtype of Object.
  3. Using == to compare the values of wrapper objects.
  4. Believing a cast changes or converts the object.
  5. Assuming successful compilation proves that a narrowing cast will succeed.
  6. Reversing widening and narrowing: subtype-to-supertype widens; supertype-to-subtype narrows.
  7. Reversing covariance and contravariance.
  8. Predicting ClassCastException for an invalid array store; the correct exception is ArrayStoreException.
  9. Assuming generic classes are covariant because arrays are.
  10. Forgetting that primitive arrays such as int[] are not subtypes of Object[].

8. What to remember for the exam

  • Wrappers adapt primitives for reference-type APIs; boxing goes primitive-to-wrapper and unboxing goes wrapper-to-primitive.
  • Wrappers are immutable, hidden conversions can cost performance, and unboxing null fails.
  • Widening is implicit and safe; narrowing needs a cast and may throw ClassCastException.
  • A cast changes the compiler's view of a reference, never the runtime object.
  • Covariance preserves subtype direction, contravariance reverses it, and invariance gives neither direction by default.
  • Java reference arrays are covariant; an unsafe store can compile but throw ArrayStoreException.
  • Always distinguish the variable's compile-time type from the object's runtime class.
