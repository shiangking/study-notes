CS2030S Guide: Wrappers, Runtime Types, Variance, and Exceptions

Primary source: supplied lecture notes for Units 20–23. Obvious transcription errors in the source code have been corrected; supplementary edge cases are marked as such.

1. The big picture

These three units expose places where Java's convenient abstractions move some safety or cost away from the line of code where it originates:

  • Wrapper classes let primitive values participate in object-based APIs, but may hide conversions, allocations, and null-related failures.
  • Narrowing casts let a program recover a concrete subtype after treating an object abstractly, but the claim may fail at runtime.
  • Array covariance lets an array of a subtype be used as an array of a supertype, but an apparently valid write can fail at runtime.
  • Exceptions separate normal logic from exceptional handling and propagate failures through method calls until an appropriate handler takes responsibility.

The shared exam strategy is to track both the compile-time type of each expression and the runtime class of the object to which it refers.

2. Unit 20 — Wrapper classes

Why wrappers exist

Java's primitive types are not classes, do not participate in inheritance, and are not subtypes of Object. A wrapper class encapsulates one primitive value in an object so that it can be used by polymorphic code or APIs requiring a reference type.

PrimitiveWrapperPrimitiveWrapper
byteBytefloatFloat
shortShortdoubleDouble
intIntegercharCharacter
longLongbooleanBoolean
 
Integer boxed = Integer.valueOf(4); // int -> Integer
int unboxed = boxed.intValue();     // Integer -> int

Autoboxing and auto-unboxing

Boxing converts a primitive to its wrapper type. Unboxing extracts a primitive from a wrapper. Java inserts these conversions automatically when required:

Integer x = 4; // autoboxing: Integer.valueOf(4)
int y = x;     // auto-unboxing: x.intValue()

int z = x + 2; // x is unboxed before arithmetic
x++;           // unbox, increment, then box the result

A wrapper object is immutable. Thus x++ does not mutate an Integer object; it produces a primitive result and assigns a wrapper for that result back to x.

Performance cost

Double sum = 0.0;
for (Integer i = 0; i < Integer.MAX_VALUE; i++) {
  sum += i;
}

This version repeatedly unboxes values for arithmetic and boxes results back into immutable wrapper objects. The concise syntax hides that work. A primitive double accumulator and int counter avoid most of the overhead and are preferable for performance-sensitive numerical code.

Equality

For primitives, == compares values. For wrapper references, == compares object identity. Use equals to compare wrapped values:

Integer a = Integer.valueOf(1000);
Integer b = Integer.valueOf(1000);

System.out.println(a == b);      // unreliable as a value comparison
System.out.println(a.equals(b)); // true

Supplementary warning: Java may cache and reuse some wrapper instances, so == may appear to work for certain values. This is exactly why it is unsafe as a general value comparison.

Null unboxing edge case

Integer n = null;
int value = n; // NullPointerException at runtime

The assignment compiles, but there is no primitive value to extract from null. This is a NullPointerException, not a ClassCastException.

3. Unit 21 — Runtime class mismatch

Abstraction forgets concrete information

GetAreable findLargest(GetAreable[] array) {
  double maxArea = 0;
  GetAreable maxObj = null;

  for (GetAreable curr : array) {
    double area = curr.getArea();
    if (area > maxArea) {
      maxArea = area;
      maxObj = curr;
    }
  }
  return maxObj;
}

The method is reusable because it works over the GetAreable interface. Its return type promises only a GetAreable, even if the returned object happens to be a Circle at runtime.

Compile-time type versus runtime class

ConceptDetermined byWhat it controls
Compile-time typeThe declaration and static type rulesWhich operations the compiler permits
Runtime classThe object actually createdDynamic method lookup and whether a narrowing cast succeeds

Widening and narrowing

Assume Circle <: GetAreable.

Circle c = new Circle(...);
GetAreable ga = c; // widening: implicit and safe

Widening from a subtype to a supertype is safe because every Circle satisfies the GetAreable contract.

GetAreable ga = findLargest(array);
Circle c = (Circle) ga; // narrowing: explicit cast required

Narrowing from a supertype to a subtype requires an explicit cast because not every GetAreable is a Circle.

What a cast means

A cast changes how the compiler is allowed to view a reference expression. It does not modify the object or convert it into an instance of another class.

GetAreable ga = new Rectangle(...);
Circle c = (Circle) ga; // compiles, then throws ClassCastException

The compiler accepts that the cast is structurally possible. At runtime, Java checks the actual object. A Rectangle is not a Circle, so the runtime check fails.

StageQuestion askedPossible outcome
Compile timeCould these reference types legally be related?Compile-time error or successful compilation
RuntimeIs this actual object compatible with the target type?Successful cast or ClassCastException

Checking before casting

if (ga instanceof Circle) {
  Circle c = (Circle) ga;
  // use c safely here
}

instanceof protects a genuinely necessary cast. However, frequent checks may signal that the abstraction does not expose the behaviour the client actually needs. Prefer using the object through its interface when possible.

Supplementary edge case: casting null to a reference type succeeds and produces null; dereferencing it later may cause NullPointerException.

4. Unit 22 — Variance

Definition

Variance describes how a subtype relationship between component types affects the relationship between complex types constructed from them. Let C(S) be a complex type formed from component type S, and suppose S <: T.

RelationshipDefinitionDirection
CovariantC(S) <: C(T)Preserves the subtype direction
ContravariantC(T) <: C(S)Reverses the subtype direction
InvariantNeither relationship follows in generalAllows neither direction by default

Java reference arrays are covariant

For Java reference arrays, if S <: T, then S[] <: T[]. Since Integer <: Object, Java therefore permits:

Integer[] intArray = {
  Integer.valueOf(10),
  Integer.valueOf(20)
};

Object[] objArray = intArray;

This is convenient for read-oriented code: anything read from an Integer[] is certainly an Object.

Why writable covariant arrays are unsafe

Integer[] intArray = { 10, 20 };
Object[] objArray = intArray;
objArray[0] = "Hello!"; // compiles, then throws ArrayStoreException

At compile time, objArray has type Object[], and a String is an Object, so the write is allowed. At runtime, the actual array object is still an Integer[]. Java checks the array's runtime component type and rejects the String with ArrayStoreException.

Operation through Object[]Compile-time resultRuntime result for actual Integer[]
Read an element as ObjectAllowedSafe: an Integer is an Object
Store an IntegerAllowedSucceeds
Store a StringAllowedArrayStoreException

Arrays versus generic collections

Arrays preserve their component type at runtime, enabling the runtime store check. Java generic classes such as List<T> are invariant by default:

List<Integer> ints = ...;
// List<Object> objs = ints; // compile-time error

The invariant rule rejects the dangerous alias at compile time. Later generic wildcard syntax provides controlled forms of covariance and contravariance.

5. Unit 23 — Exceptions

Why exceptions improve program structure

Traditional error handling often uses special return values and global state such as C's errno. This creates two problems:

  • the normal task becomes interspersed with repetitive error checks; and
  • every caller must remember what each special value means and check it correctly.

Exceptions keep the main operation together and move exceptional responses into separate handlers:

try {
  reader = new FileReader(filename);
  scanner = new Scanner(reader);
  value = scanner.nextInt();
} catch (FileNotFoundException e) {
  System.err.println("Unable to open " + filename + ": " + e);
} catch (InputMismatchException e) {
  System.err.println("Unable to scan for an integer");
} catch (NoSuchElementException e) {
  System.err.println("No input found");
} finally {
  if (scanner != null) {
    scanner.close();
  }
}

The try block states the normal task. Each catch block describes a response to one family of failures. The optional finally block performs cleanup whether the try completes normally or abruptly.

try, catch, and handler selection

Exceptions are objects. Information about the failure—including a message and stack trace—is encapsulated in the thrown object and made available through the catch parameter, such as e.

Catch clauses are examined from top to bottom. Java selects the first clause whose parameter type is the same as, or a supertype of, the runtime class of the thrown exception. Therefore, more specific handlers must appear before more general handlers.

// Illegal: ExceptionX <: ExceptionY, so the second handler is unreachable.
try {
  riskyOperation();
} catch (ExceptionY e) {
  // also catches every ExceptionX
} catch (ExceptionX e) {
  // compile-time error: already caught
}

Multi-catch

If unrelated exception types require the same response, combine them using |:

catch (FileNotFoundException | NoSuchElementException e) {
  System.err.println(e);
}

Correction to the raw notes: InputMismatchException extends NoSuchElementException. Java forbids related alternatives in one multi-catch because the subtype is already covered, so listing both would not compile.

throw versus throws

KeywordPurposeExample
throwActually raises one exception object nowthrow new IllegalArgumentException(...);
throwsDeclares that a method or constructor may propagate exception types to its calleropenFile(...) throws FileNotFoundException
 
class Circle {
  private Point c;
  private double r;

  public Circle(Point c, double r) {
    if (r < 0) {
      throw new IllegalArgumentException("radius cannot be negative");
    }
    this.c = c;
    this.r = r;
  }
}

Executing throw stops normal execution at that statement. The field assignments are skipped, and the exception begins propagating to the caller. Since IllegalArgumentException is unchecked, declaring it with throws is optional.

Checked versus unchecked exceptions

PropertyChecked exceptionUnchecked exception
HierarchySubclass of Exception, but not RuntimeExceptionSubclass of RuntimeException
Typical meaningExternal or anticipated failure that valid code may still encounterUsually a programming error or violated precondition
Compiler ruleMust be caught or declared with throwsNeed not be caught or declared
ExamplesFileNotFoundExceptionIllegalArgumentException, NullPointerException, ClassCastException

The course's practical distinction is that checked exceptions represent situations a correct program should actively anticipate, whereas unchecked exceptions usually reveal a defect or invalid use of an abstraction. This is a design guideline, not a claim that every real-world case fits perfectly into one category.

Exceptions are part of a method contract

A method contract includes parameter types, return type, behaviour, and exceptional outcomes. The compiler enforces checked-exception contracts:

static FileReader openFile(String filename)
    throws FileNotFoundException {
  return new FileReader(filename);
}

Every caller must now either catch FileNotFoundException or explicitly propagate it. Adding a new checked exception therefore changes the public specification and may require changes throughout the caller chain.

An overriding method may declare only the same checked exceptions, more specific checked exceptions, or fewer checked exceptions than the overridden method. It may not introduce a broader or unrelated checked exception. This preserves Liskov substitution: a client using the supertype must not face a new checked obligation.

Handle or pass the buck?

When a method cannot respond meaningfully, it may propagate the exception to a caller:

static FileReader openFile(String filename)
    throws FileNotFoundException {
  return new FileReader(filename);
}

public static void main(String[] args) {
  try {
    openFile("input.txt");
  } catch (FileNotFoundException e) {
    // warn the user and allow another file to be selected
  }
}

Handle an exception at the lowest level that can meaningfully recover, restore a valid state, translate the failure, retry, or give an appropriate user-facing response. If the current method cannot do any of these, propagate it instead of pretending it has been handled.

Do not merely let every layer—including main—declare throws. If nobody handles a checked exception, the user receives an implementation-oriented stack trace rather than a controlled response.

Exception control flow and stack unwinding

try {
  m1();
} catch (E1 e) {
  handleE1();
} catch (E2 e) {
  handleE2();
} finally {
  cleanUp();
}

Suppose m1() calls m2(), which calls m3(), which calls m4(), and m4() throws E2:

  1. Normal execution in m4() stops at the throw.
  2. The JVM searches the current method for a compatible handler.
  3. If none exists, its stack frame is unwound and the search continues in its caller.
  4. This repeats through m3(), m2(), and m1().
  5. The compatible catch (E2 e) executes.
  6. The finally block executes, then control continues after the whole statement unless another abrupt action occurs.

Statements skipped by stack unwinding are not resumed later. A finally block also executes when the associated try or catch uses return or throws again.

Supplementary precision: “finally always runs” has rare exceptions, such as forced JVM termination. For ordinary exam traces involving normal completion, return, or throw, treat it as executing.

Creating a custom exception

Create a custom type only when it communicates a domain-specific failure or carries useful information that existing exception types cannot express:

class IllegalCircleException extends IllegalArgumentException {
  private Point center;

  IllegalCircleException(Point center, String message) {
    super(message);
    this.center = center;
  }

  @Override
  public String toString() {
    return "The circle centered at " + this.center
        + " cannot be created: " + getMessage();
  }
}

Extending IllegalArgumentException makes this custom exception unchecked. Extending Exception directly would make it checked.

Do not break the abstraction barrier

class ClassRoster {
  public Student[] getStudents() throws FileNotFoundException {
    // implementation reads a file
  }
}

This leaks the implementation detail that the roster is stored in a file. If the class later reads from a database, callers must change despite the abstract operation—getting students—remaining the same. Prefer handling or translating implementation-specific exceptions inside the abstraction:

public Student[] getStudents() throws RosterAccessException {
  try {
    return readStudentsFromFile();
  } catch (FileNotFoundException e) {
    throw new RosterAccessException("Unable to load roster", e);
  }
}

The public exception now describes the abstraction's failure rather than its current storage mechanism.

Resource cleanup

If a method acquires a resource, it remains responsible for releasing it even when an exception propagates. A finally block can perform this cleanup and then allow the same exception to continue upward.

Supplementary modern Java: for resources implementing AutoCloseable, prefer try-with-resources because Java closes them automatically:

try (Scanner scanner = new Scanner(new FileReader(filename))) {
  return scanner.nextInt();
}

7. Step-by-step exam procedures

  1. Write down the compile-time type of every relevant variable and expression.
  2. Write down the runtime class of every created object or array.
  3. Mark every implicit boxing or unboxing conversion.
  4. For a cast, check whether the actual object is an instance of the target type.
  5. For an array write, check the array object's actual runtime component type.
  6. Name the exact failure: NullPointerException, ClassCastException, or ArrayStoreException.
  7. For an exception trace, stop at the throw, unwind callers until the first compatible catch, then execute applicable finally blocks.
  8. For a checked exception, verify that every path either catches it or declares it with throws.
  9. Ask whether the current layer can respond meaningfully; if not, propagate or translate without leaking implementation details.

8. Common mistakes and exam traps

  1. Writing Int instead of Java's primitive type int.
  2. Assuming a primitive is a subtype of Object.
  3. Using == to compare the values of wrapper objects.
  4. Believing a cast changes or converts the object.
  5. Assuming successful compilation proves that a narrowing cast will succeed.
  6. Reversing widening and narrowing: subtype-to-supertype widens; supertype-to-subtype narrows.
  7. Reversing covariance and contravariance.
  8. Predicting ClassCastException for an invalid array store; the correct exception is ArrayStoreException.
  9. Assuming generic classes are covariant because arrays are.
  10. Forgetting that primitive arrays such as int[] are not subtypes of Object[].
  11. Confusing throw (raise one object) with throws (declare possible propagation).
  12. Placing a general catch before a specific catch, making the latter unreachable.
  13. Swallowing failures with catch (Exception e) { }—“catch-them-all” or Pokémon exception handling.
  14. Calling System.exit in a handler, which prevents higher layers from responding or cleaning up.
  15. Using exceptions for expected control flow, such as catching NullPointerException instead of checking whether a reference is null.
  16. Exposing implementation-specific exceptions across an abstraction boundary.
  17. Declaring a checked exception all the way through main instead of producing a meaningful user-facing response.

9. What to remember for the exam

  • Wrappers adapt primitives for reference-type APIs; boxing goes primitive-to-wrapper and unboxing goes wrapper-to-primitive.
  • Wrappers are immutable, hidden conversions can cost performance, and unboxing null fails.
  • Widening is implicit and safe; narrowing needs a cast and may throw ClassCastException.
  • A cast changes the compiler's view of a reference, never the runtime object.
  • Covariance preserves subtype direction, contravariance reverses it, and invariance gives neither direction by default.
  • Java reference arrays are covariant; an unsafe store can compile but throw ArrayStoreException.
  • Always distinguish the variable's compile-time type from the object's runtime class.
  • Checked exceptions must be caught or declared; unchecked exceptions do not have that compiler requirement.
  • Catch clauses are tested top-to-bottom, so specific exception types must come before general ones.
  • throw stops normal execution; the JVM unwinds the stack until it finds the first compatible handler.
  • finally is for cleanup and normally executes after normal completion, return, or throw.
  • Handle an exception at the lowest layer capable of a meaningful response; otherwise propagate or translate it.
  • Do not swallow exceptions, use them for normal control flow, expose implementation details, or abandon checked exceptions at main.
